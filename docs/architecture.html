01

Request lifecycle

The React UI never talks to retrieval, personalization, or the LLM directly — it only ever calls five FastAPI routes. Every one of those routes that answers a query does it by invoking the same compiled LangGraph, once synchronously (/api/query) and once as a live stream (/api/query/stream, which drives the UI's trace panel off graph.stream() directly — not a simulated progress bar).

02

Three-tier routing

This is the graph's actual branch structure, node for node. The router (app/agent/router.py) picks a tier from cheap rule-based signals first; only a genuinely borderline query ever reaches a classifier, and that classifier is tried cheap-first too — a trained learned router before the real LLM. The three lanes below aren't a simplification: fast skips straight from retrieval to a rule-based explanation with zero LLM calls; deep is the only lane that ever calls the LLM, and it calls it twice.

fast — exact filename or clean filter, ≤9 words standard — learned router (conf ≥ 0.6) or LLM classify deep — vague/conversational, or ≥14 words
03

Retrieval fan-out, fusion & the rerank bypass

Inside standard_retrieve/deep_retrieve, up to four retrievers run independently and get merged by Reciprocal Rank Fusion — no library, scores are rank-based so BM25 and cosine similarity never need to share a scale. The one non-obvious branch: image-sourced candidates skip the cross-encoder entirely. It was added after a real bug — the reranker only ever sees filename + extracted_text, which for an image is just its caption, so it was overriding correct CLIP visual matches with an irrelevant text judgment (full-pipeline NDCG@10 on image queries was ~0.30 despite the isolated CLIP retriever scoring ~0.83 on the same queries).

04

LLM backend: one chokepoint, two providers

Every LLM call in the system — router fallback classification, deep-tier query enrichment, deep-tier explanation generation, and synthetic data generation — goes through exactly one function, so the "fast route makes zero LLM calls" claim is auditable rather than asserted. LLM_BACKEND is read fresh from the environment on every call, not frozen at import, and defaults to local per the course constraint that the primary system run fully on-device.

05

Deployment topology

Four Docker Compose services boot in a strict, health-gated order — not just "started," but ready. ollama-pull is a one-shot init container: it waits for Ollama's own healthcheck, pulls the model, and exits; api then waits for that pull to complete successfully, not merely for Ollama to be healthy, so the first real query never races a still-downloading model.

06

Data model

One SQLModel schema (app/models.py) backs both the synthetic demo corpus and any real ingested folder — retrieval, personalization, and routing code never touch a DataSource directly, only these rows. Vector search lives in two separate Chroma collections, not one, because the text and image embedders don't share a dimensionality.
